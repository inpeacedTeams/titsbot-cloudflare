# Chat v2: WPM, опечатки и восстановление

## Обновление работающего бота

1. По возможности обновляйтесь между тестами, не во время активной минуты набора. Завершённые результаты и D не сбрасываются.
2. В папке проекта выполните `git pull origin main`. Если есть конфликт, остановитесь: не используйте `git reset --hard`, сохраните локальные настройки.
3. Откройте `supabase/migrations/002_chat_v2.sql`, скопируйте весь файл в Supabase SQL Editor и выполните от владельца базы. Для существующей базы НЕ запускайте заново 001_initial.sql. Миграция 002 добавляет два поля и два состояния, не удаляет таблицы, данные или D; повторный запуск безопасен.
4. Выполните `npm run check`, `npm test`, затем `npm run deploy`.
5. Проверьте `/readyz`: ожидается `{"ok":true,"database":true}`. При отсутствии миграции новая проверка сообщит DB_COLUMN_MISSING.
6. Новые или ещё не завершённые Chat Tests будут обработаны по chat-typos-v2. Уже завершённые тесты, даже с плохой прежней оценкой, остаются неизменными. Это обновление НЕ выдаёт новые попытки завершившим калибровку.

`wrangler.jsonc`, токены, Hyperdrive и настройки BotFather менять не нужно. Для новой пустой установки выполните сначала 001_initial.sql, потом 002_chat_v2.sql, затем настройку серверной роли. Обе миграции также подключены к интеграционным тестам.

## WPM

WPM = сумма символов сообщений / 5 / (длительность / 60). Окно теста — 60 секунд после GO. Под символом понимается видимый Unicode-символ (графема): составной emoji считается одним символом. Пробелы, переносы строк, пунктуация, эмодзи считаются. Между сообщениями искусственные пробелы не добавляются. Учитывается исходный полученный текст и подписи к медиа участника, включая повторы, команды и пересланный текст, если они попали в окно. Правки не прибавляют символов и не подменяют исходный текст.

Чужие сообщения, боты, сообщения до GO и после конца окна не входят в тест. Доставка принимается ещё 5 секунд. Telegram не раскрывает нажатия клавиш: вставку, диктовку и заранее набранный текст нельзя надёжно отличить от ручного ввода. Без исключений и штрафов этот показатель нельзя считать защищённым от накрутки.

Короткие повторы не исключаются. Для длинных нормализованных текстов от 80 символов сходство >=95% с одним из последних 20 длинных сообщений отмечается отдельным счётчиком. Повторы НЕ вычитаются из WPM. Ритм отправки (шесть 10-секундных окон) и разнообразие слов остаются отдельными компонентами Score; они не являются скоростью нажатий. Вес WPM, порог нормирования Score и схема D сохранены из конфигурации пользователя. Показанный WPM не обрезается; компонент WPM в Score по-прежнему ограничен 0..100.

## Accuracy: только вероятные опечатки

Модель НЕ назначает процент. Она возвращает предполагаемые опечатки с ID сообщения, номером слова, исходным словом, исправлением и уверенностью. Сервер проверяет совпадение исходного слова, отклоняет неизвестные/дублированные ссылки, игнорирует низкую уверенность (<0.95), многословные переписывания, смену регистра и е/ё. Допускаются небольшие исправления расстоянием 1–2; перестановка соседних букв считается одной операцией.

Accuracy = max(0, 100 × (1 − предполагаемые буквенные исправления / количество букв в исходных сообщениях)). Пробелы и пунктуация не входят в знаменатель Accuracy, но входят в WPM. Таким образом пунктуационные или грамматические замечания не должны понижать Accuracy. Грамматика, содержание, факты, сленг, имена, стиль и пунктуация явно исключены из задания модели. Это консервативная оценка по тексту, НЕ объективная точность клавиатурного ввода: модель всё равно может ошибаться в намерении автора. Уверенность модели не является калиброванной вероятностью. 100% означает отсутствие найденных высокоуверенных опечаток, а не доказанную безошибочность.

В отчёте показываются число предполагаемых исправлений и до пяти примеров. Полный список и версия методики сохраняются в analysis. Нет букв — Accuracy недоступна и окончательный Chat D не назначается. Для слишком большого запроса (>64000 символов сериализованного запроса с токенами) текст не урезается молча: WPM сохраняется, анализ заканчивается ошибкой без искусственного нуля. Повтор того же неподдерживаемого текста сам по себе не устранит ограничение.

## Один Chat Test и таймер

Блокировка действует на подготовку и набор Chat Test в одной группе. При занятости бот сообщает оставшееся время (для запущенного теста — до конца минуты плюс 5 секунд на доставку). Новый участник не тратит попытку. Блокировка защищена транзакцией PostgreSQL, блокировкой по группе и уникальным индексом. После фиксации сообщений следующий Chat Test разрешён, даже если предыдущий ещё проверяется моделью. MT не блокируется этим ограничением.

## Таймауты

- Подготовка GO: 30 секунд от резервирования. Незавершённый старт переводится в CANCELLED, задание отправки отменяется. Следующий /getdchat может повторить незапущенную попытку. Подготовительные сообщения отменённого запуска очищаются при повторном запуске.
- Анализ: 120 секунд на серию, максимум три обычные попытки запроса; каждый HTTP-запрос ограничен 20 секундами. При исчерпании — ANALYSIS_FAILED, исходный текст и WPM остаются, Accuracy недоступна, D не фиксируется.
- /getdchat после ошибки анализа повторяет только анализ того же сохранённого текста, не создаёт новую минуту набора.
- DO alarm и минутный Cron восстанавливают работу после сбоя. Дедлайны проверяются по базе; фактическое уведомление может задержаться при недоступности платформ или Telegram. Просроченный результат анализа не фиксируется. Fencing токен задания защищает от подтверждения устаревшего обработчика; доставка Telegram остаётся at-least-once, поэтому редкие повторы сообщений возможны.

В PostgreSQL integration suite добавлены миграция 002, отказ с таймером, отмена старта, повтор незапущенной попытки, освобождение группы во время анализа и восстановление анализа без потери WPM.
